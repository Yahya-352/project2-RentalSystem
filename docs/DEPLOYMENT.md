# Deployment Guide

How to build RentRide, run it locally, and deploy it to AWS.

## Quick start (AWS)

```bash
git clone https://github.com/Yahya-352/project2-RentalSystem.git && cd project2-RentalSystem
cp infra/terraform.tfvars.example infra/terraform.tfvars    # fill in the secrets
cd infra && terraform init && terraform apply && cd ..      # about 15 minutes
./scripts/release.sh                                        # build, push, deploy, publish frontend
terraform -chdir=infra output app_url                       # open this URL
```

The rest of this guide explains each step.

---

## 1. Architecture

| Component | Where it runs |
|---|---|
| user, car, booking, payment, notification, audit services | Docker containers on one EC2 instance (`docker-compose.prod.yml`) |
| Kafka | container on the same EC2 instance, reachable only inside Docker |
| PostgreSQL | Amazon RDS in private subnets, reachable only from the EC2 security group |
| Docker images | Amazon ECR, one repository per service, immutable version tags |
| Secrets and settings | SSM Parameter Store under `/rentride/app/`, read by the instance role |
| Frontend | S3 bucket behind CloudFront; CloudFront also routes `/api/*` to the services |
| Logs and alarms | CloudWatch Logs group `/rentride/app`, error metric and alarms |

All infrastructure is defined with Terraform in `infra/`.

## 2. Prerequisites

| Tool | Version | Used for |
|---|---|---|
| Git | any | cloning the repository |
| Docker Desktop (with Compose v2) | 24+ | building images, running locally |
| Java | 21 | building services outside Docker (optional) |
| Node.js | 20+ | building the frontend |
| Terraform | 1.7+ | creating the AWS infrastructure |
| AWS CLI | v2 | pushing images, deploying |

AWS access: an IAM user with permission to create the resources in `infra/` (administrator access is simplest for the first setup), configured locally:

```bash
aws configure            # access key, secret key, region eu-north-1
aws sts get-caller-identity
```

## 3. Build the application

Every service depends on the shared `common` module, so build it first:

```bash
cd common && ./mvnw install -DskipTests && cd ..
cd booking-service && ./mvnw verify && cd ..     # repeat for each service
```

`verify` compiles, runs the tests (unit, concurrency and Cucumber scenarios) and packages the jar.

## 4. Build the Docker images

One shared `Dockerfile` builds every service; the service name and port are build arguments:

```bash
docker build --build-arg SERVICE=booking-service --build-arg PORT=8083 -t rentride/booking-service:1.0.0 .
```

Or build all six at once with Compose:

```bash
docker compose build
```

## 5. Run locally

Docker Compose starts PostgreSQL, Kafka and all six services:

```bash
# root .env: the password for the local PostgreSQL container
echo "DB_PASSWORD=choose-a-password" > .env
# each service reads its own .env (DB_USERNAME, DB_PASSWORD, JWT_SECRET, ...)
docker compose up --build -d
docker compose ps
```

| Service | Port |
|---|---|
| user-service | 8081 |
| car-service | 8082 |
| booking-service | 8083 |
| payment-service | 8084 |
| notification-service | 8085 |
| audit-service | 8086 |
| PostgreSQL | 5433 on the host |
| Kafka | 9094 on the host (19092 inside Docker) |

Frontend (proxies `/api` to the services):

```bash
cd frontend && npm install && npm run dev      # http://localhost:5173
```

Stop with `docker compose down` (add `-v` to delete the local database).

### Starting Kafka on its own

Kafka is part of `docker-compose.yml`. To run only Kafka, for example while running the services from an IDE:

```bash
docker compose up -d kafka
```

Services started outside Docker connect to `localhost:9094`, so set `SPRING_KAFKA_BOOTSTRAP_SERVERS=localhost:9094`.

## 6. Configure AWS

Copy the example variables file and fill in the values:

```bash
cp infra/terraform.tfvars.example infra/terraform.tfvars
```

| Variable | Meaning |
|---|---|
| `aws_region` | region for every resource (`eu-north-1`; must match `AWS_REGION` in `Jenkinsfile`) |
| `instance_type` | `t3.medium` recommended; `t3.micro` is free tier but slow for six services plus Kafka |
| `smtp_username`, `smtp_password` | mail account used for verification and password emails |
| `admin_username`, `admin_password` | the admin account created on first start |
| `seed_password` | password of the seeded demo customer and agency accounts |
| `stripe_secret_key` | Stripe test secret key (`sk_test_...`) |
| `stripe_webhook_secret` | signing secret of the Stripe webhook endpoint (see step 9) |
| `alert_email` (optional) | receives CloudWatch alarm notifications |

`terraform.tfvars` and the Terraform state contain secrets and are ignored by Git. The database password, JWT secret and internal API key are generated by Terraform and never need to be typed.

## 7. Create the infrastructure

```bash
cd infra
terraform init
terraform plan        # review
terraform apply       # about 15 minutes, CloudFront takes the longest
terraform output
cd ..
```

This creates the VPC, security groups, IAM role, RDS, EC2 (with Docker, Compose, swap and CloudWatch logging), ECR repositories, SSM parameters, the S3 bucket, CloudFront, and the CloudWatch log group and alarms.

## 8. Deploy the services and the frontend

```bash
./scripts/release.sh                     # tag 1.0.<timestamp>
IMAGE_TAG=1.1.0 ./scripts/release.sh     # or choose a version
```

The script:

1. builds the six images for `linux/amd64`;
2. pushes them to ECR as `rentride/<service>:<tag>`;
3. sends `docker-compose.prod.yml` and `deploy.sh` to the EC2 instance through SSM Run Command (no SSH) and runs `deploy.sh`, which loads the settings from SSM, logs in to ECR with the instance role and starts the containers;
4. builds the frontend and uploads it to S3, then invalidates the CloudFront cache.

On Windows, run it from Git Bash. The first deployment on a new instance waits a few minutes for the server to finish its setup.

## 9. Stripe webhook

Payments are confirmed by a Stripe webhook:

1. Stripe Dashboard → Developers → Webhooks → Add endpoint: `<app_url>/api/pay/webhook`
2. Events: `checkout.session.completed`, `checkout.session.expired`
3. Copy the endpoint's signing secret into `stripe_webhook_secret` in `terraform.tfvars`
4. `terraform -chdir=infra apply`, then `./scripts/release.sh` so the services reload the settings

## 10. Verify the deployment

```bash
terraform -chdir=infra output app_url
```

1. Open the URL and log in as the admin account from `terraform.tfvars`. The seeded customer (`customer@rental.com`) and agency (`agency@rental.com`) use `seed_password`.
2. Browse cars (six demo cars are seeded), create a booking as the customer, approve it as the agency, pay with a Stripe test card (`4242 4242 4242 4242`).
3. As admin, open the audit log: the booking and payment events appear.

On the server (EC2 → Connect → Session Manager):

```bash
cd /opt/rentride && sudo docker compose -f docker-compose.prod.yml ps
```

## 11. CI/CD with Jenkins

`Jenkinsfile` runs on every push (polling every two minutes):

| Stage | Action |
|---|---|
| Build common | installs the shared module |
| Backend: Build and Test | `./mvnw verify` for all services in parallel; a failing test stops the pipeline |
| Backend: Build Images | `docker compose build` |
| Deploy to AWS | only when the `DEPLOY` parameter is ticked: runs `scripts/release.sh` with tag `1.0.<build number>` |

Setup:

1. Run Jenkins on an EC2 instance with Docker access. The image in `jenkins/` contains everything the pipeline needs (Java 21, Docker CLI with Compose, AWS CLI, Node.js):
   ```bash
   docker build -t rentride-jenkins ./jenkins
   docker run -d --name jenkins --restart unless-stopped -u root -p 8080:8080 \
     -v jenkins_home:/var/jenkins_home -v /var/run/docker.sock:/var/run/docker.sock rentride-jenkins
   ```
2. Attach an IAM role to the Jenkins instance (`rentride-jenkins-role`) instead of storing access keys. It needs: ECR push to the `rentride/*` repositories, `s3:PutObject`/`DeleteObject`/`ListBucket` on the frontend bucket, `cloudfront:CreateInvalidation`, `ssm:SendCommand`, `ssm:GetCommandInvocation`, `ssm:DescribeInstanceInformation` and `ec2:DescribeInstances`.
3. Plugins: Pipeline, Git.
4. Set `AWS_REGION`, `FRONTEND_BUCKET` and `CLOUDFRONT_ID` in `Jenkinsfile` from `terraform output`.
5. New Item → Pipeline → "Pipeline script from SCM" → this repository, script path `Jenkinsfile`. The job polls the repository every two minutes; a GitHub webhook can replace polling because the Jenkins instance is reachable from the internet.

## 12. Logs and monitoring

| What | Where |
|---|---|
| Container logs of every service | CloudWatch → Log groups → `/rentride/app` → one stream per container |
| Errors | metric `RentRide/AppErrorCount` and alarm `rentride-app-errors` |
| Server health | alarms `rentride-ec2-cpu-high` and `rentride-ec2-status-check` |
| Kafka activity | CloudWatch Logs Insights on `/rentride/app`, e.g. `filter @message like /kafka/` |
| Live container logs | Session Manager → `sudo docker compose -f /opt/rentride/docker-compose.prod.yml logs -f booking-service` |

Locally: `docker compose logs -f <service>`.

## 13. Updating and removing

- New version: `IMAGE_TAG=1.2.0 ./scripts/release.sh`. Tags are immutable, so every release needs a new tag.
- Changed settings or secrets: edit `terraform.tfvars`, `terraform apply`, then run the release again.
- Remove everything: `terraform -chdir=infra destroy`.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `release.sh` waits for SSM for a long time | the instance is still booting; it continues automatically once the SSM agent is online |
| Image push rejected: tag already exists | ECR tags are immutable; use a new `IMAGE_TAG` |
| Services restart repeatedly | instance too small: set `instance_type = "t3.medium"` and apply |
| API returns 502 through CloudFront right after a deploy | the services take a minute or two to start |
| After stopping and starting the EC2 instance, the API is unreachable | its public DNS name changed: run `terraform apply` so CloudFront uses the new one |
